## 1. 项目背景

### 1.1 需求背景

本项目服务的是一套**地方性麻将玩法**。它不在腾讯麻将等主流平台的标准规则集内：东风、中发白在这套玩法里是"花牌"，春夏秋冬梅兰竹菊参与杠开，计分采用独有的"花数"体系。因此，既没有现成的开源引擎可以完整复用，也没有现成的策略工具可以直接使用。

同时，真实对局中的决策压力是具体的：

1. 手牌该打哪张——既要推进自己的牌型，又要避免点炮；
2. 对手在做什么牌——从弃牌和明牌推断各家意图；
3. 花牌什么时候杠——早杠稳拿花分，留到听牌再杠搏杠开；
4. 局面信息量大——144 张牌、三家对手的弃牌与明牌、剩余张数，人脑很难算全。

一个"像老手一样"的策略助手需要同时做到**算得准**（向听数、进张、剩余张数不容出错）和**读得懂**（结合局面的推理与解释）。这两件事分别适合程序和大语言模型，不适合任何一方单独完成。

### 1.2 演进背景

项目经历了四个阶段，每一阶段都暴露并解决了特定问题：

| 阶段 | 内容 | 暴露的关键问题与修正 |
|---|---|---|
| 概要设计 | 规则定义、混合架构构想 | 中发白/东风列为花牌，但早期实现计划的测试用例却把它们当可组牌——规则自相矛盾，以设计文档为准修正 |
| 早期实现计划 | 9 个 TDD 任务 | 向听数公式是会算错的占位实现（`8 - pairs - pungs*2`），`parse_tile` 含无效语法——全部废弃重写 |
| Phase 1：核心引擎 | 牌模型、正确向听、剩余牌统计 | 从零实现"分解计数"向听算法，用用户手算牌例（23456→听1,4,7）锚定正确性 |
| Phase 2 及以后 | LLM 顾问、CLI、明牌、风险估计、完整计分 | 发现向听公式在明牌场景缺 `-2×明牌数` 项（此前从未触发）；计分规则通过与用户逐条确认补全 |

### 1.3 核心矛盾

系统必须同时满足三个目标：

| 目标 | 主要手段 | 单独使用时的问题 |
|---|---|---|
| 计算准确 | 确定性引擎（向听、剩余张数、计分） | 只会算数，不会读牌、不会解释 |
| 局面理解 | 大语言模型读牌推理 | 算不准向听数和剩余张数，幻觉风险高 |
| 规则贴合 | 地方玩法的完整规则系统 | 通用麻将库与开源引擎均不匹配 |

总体设计的本质是**分层**：数字由引擎决定，判断由 LLM 完成，规则由本文档冻结。

## 2. 产品愿景与产品定义

### 2.1 产品愿景

让玩家在对局中，只需输入当前局面（手牌、各家弃牌与明牌、持有的花牌），就能得到一份**数字准确、推理可信、像老手口吻**的出牌建议——包括打哪张、为什么、风险多大、杠该不该现在开。

### 2.2 产品定义

系统名称：麻将策略助手（Mahjong Advisor）。

标准输入（一局快照）：

```text
我的暗牌：2万 3万 4万 5万 6万 6万 6万 1饼 1饼 1饼 2条 2条 2条
我的明牌：peng 5饼（如无则省略）
我的花牌（未杠）：中 中 中 中（如无则省略）
上家弃牌：9万 1饼 …
下家弃牌：…
对家弃牌：…
```

标准输出：

1. **【分析结果】**：向听数/听牌与所胡牌、进张、出牌候选排序、每张候选的被吃/被碰/点炮风险估计、剩余张数、杠开机会——全部来自确定性引擎；
2. **【AI建议】**：LLM 综合局面给出的读牌推理与 3-5 个出牌/杠牌建议及理由；
3. **无 API key 或网络不可用时**：优雅降级为仅输出【分析结果】+ 给模型的 Prompt 预览，不崩溃。

### 2.3 核心价值

- 对玩家：把"凭感觉打牌"升级为"数字 + 推理"的双层决策；
- 对本项目：形成一套可测试、可追溯、可扩展的地方麻将规则系统与策略引擎。

## 3. 目标与非目标

### 3.1 核心目标

1. 向听数、听牌、进张、剩余张数的计算**零错误**——这些数字是所有建议的地基；
2. 计分系统与本玩法实际规则**逐条一致**（见第 9 章）；
3. LLM **不参与任何数值计算**，只做读牌、权衡与解释；
4. 支持明牌（吃/碰/杠）后的局面分析；
5. 识别"留花/择时杠"机会并给出量化对比；
6. 命令行一条链路跑通：输入 → 分析 → 建议；
7. 无网络/无 key 环境可正常使用引擎分析部分。

### 3.2 质量目标

| 指标 | 目标 |
|---|---:|
| 向听数正确率（基准牌例集） | 100% |
| 听牌并集正确率（多拆法牌例） | 100% |
| 剩余张数正确率 | 100% |
| 计分与确认规则的一致性 | 100% |
| 单测数量（当前） | 178 项全绿 |
| LLM 建议中的数值来源 | 100% 来自引擎注入 |

### 3.3 非目标

本系统不是：

- 通用麻将规则引擎（只服务这一套地方玩法，规则硬编码于本文档口径）；
- 实时对局客户端（不接入任何游戏平台，输入靠手工）；
- 精确胜率模拟器（风险是透明启发式，不做蒙特卡洛全枚举——见第 11 章的边界说明）；
- 计分仲裁工具（计分实现以本文档口径为准，真实牌局争议以线下规则为准）。

### 3.4 "读牌"的承诺边界

LLM 的对手推断是**启发性判断**，不是读心术。系统承诺的是：给 LLM 的局面事实完整、准确（弃牌序列、明牌、剩余张数、风险估计），LLM 在此之上的推理质量由模型能力与 Prompt 约束保证；不承诺推断必定命中对手实际牌型。

## 4. 用户与使用场景

### 4.1 目标用户

- **本项目玩家本人**：熟悉这套地方玩法，对局中需要快速、可信的决策辅助；
- **同玩法牌友**：未来通过 Web UI / 拍照输入使用的次级用户。

### 4.2 核心使用场景

1. 摸牌后（14 张暗牌）：该打哪张？
2. 听牌后：胡哪些牌、各家还有几张活牌？
3. 持有花牌/杠料：现在杠还是留到听牌搏杠开？
4. 对手弃牌变多：谁可能听牌了、哪张牌危险？
5. 胡牌后：这把值多少花？

## 5. 产品形态与交互流程

### 5.1 命令行交互

```bash
export ANTHROPIC_API_KEY=your_key      # 或 ant auth login；不设则离线降级
python -m src.main
# 可选：换更省更快的模型（默认 claude-opus-5）
export MAHJONG_ADVISOR_MODEL=claude-sonnet-5
```

交互序列：暗牌 → 花牌（未杠）→ 自己的明牌 → 上家/下家/对家弃牌 → 输出。

### 5.2 输入语法

| 类别 | 写法 | 说明 |
|---|---|---|
| 数字牌 | `3万` `9条` `1饼` | 空格分隔 |
| 风牌 | `南风` 或 `南` | 两种都接受 |
| 三元/季节花 | `中` `发` `白` `春` … | 单字 |
| 明牌 | `peng 5饼`、`chi 3万 4万 5万`、`ming_gang 9条`、`an_gang 南风` | 多组用空格或逗号（全角亦可）分隔 |
| 手牌 | 只输**暗牌** | 碰过之后向听按"还差 4−明牌数 组面子"计算 |

### 5.3 输出结构

```text
【分析结果】
听牌！胡：1万 2万 4万 5万 7万
全桌剩余牌：130 张
出牌候选（按打出后向听数排序）：
  - 打 2万：打出后向听数 0；点炮风险 中（被吃6% 被碰18% 点炮13%）
杠牌/杠开机会：
  - 花牌自杠 中：杠分 12花；留4张=6花 / 杠=12花；留到听牌杠搏杠开
  ★ 已听牌：现在杠任意一组，补牌成胡 = 杠开（底分8花，上不封顶叠加）

【AI建议】（LLM 输出；失败时降级为 Prompt 预览）
```

## 6. 总体设计原则

1. **数字与判断分离**：向听、进张、剩余、风险、花数全部由确定性引擎计算；LLM 不得成为任何数值的来源。
2. **规则由文档冻结**：玩法规则（尤其计分）以本文档口径为实现与测试的唯一依据；任何规则变更先改文档与测试，再改实现。
3. **正确性用用户牌例锚定**：`23456→听1,4,7`、`2345666→听1,2,4,5,7` 等经用户手算确认的牌例固化为测试，防止引擎退化。
4. **启发式必须透明**：所有概率估计公式写进 docstring，标注"非精确概率"，可被质疑与校准。
5. **优雅降级**：LLM 层任何失败（无 key、断网、拒绝）都不影响引擎分析的使用。
6. **明牌是一等公民**：向听、剩余、计分从设计之初就支持吃/碰/杠后的局面，而非事后补丁。

```text

   │
   ▼

│ hand_analyzer.py  向听数（标准形+七对）、进张、听牌、出牌排序  │
│ probability.py    剩余张数、被吃/被碰/点炮风险估计            │
│ scoring.py        花数计分（底分/番型/杠分/花牌/风刻）        │
└──────────────────────────┬───────────────────────────────────┘
                           │ AnalysisBundle（结构化事实）
            ┌──────────────┴──────────────┐
            ▼                             ▼
   CLI【分析结果】               advisor.py（src/llm/）
   （main.py）                   build_prompt：规则+局面+引擎事实
                                 get_advice：Claude API（注入式 client）
                                 find_kong_opportunities：杠开机会
                                 │
                                 ▼
                        【AI建议】/ 失败降级为 Prompt 预览
```

### 7.1 逻辑分层

| 层 | 责任 | 模块 |
|---|---|---|
| 数据层 | 牌与局面的表示 | `tiles.py` |
| 分析层 | 向听/进张/听牌/出牌排序 | `hand_analyzer.py` |

## 8. 玩法规则系统（本变体唯一权威口径）

> 本章是全部规则的冻结口径。与早期文档冲突处，以本章为准。

### 8.1 牌的构成（144 张）

| 类型 | 张数 | 说明 |
|---|---:|---|
| 万 / 饼 / 条 | 108 | 每门 1-9 各 4 张，可顺子可刻子 |
| 东、南、西、北 | 16 | **东是花牌**；南西北是普通字牌 |
| 中、发、白 | 12 | **全部是花牌**（本变体与标准麻将的根本差异） |
| 春夏秋冬梅兰竹菊 | 8 | 花牌，每张仅 1 张 |
| **花牌合计** | **24** | 东风4 + 中发白12 + 季节8 |

### 8.2 可组牌与胡牌结构

- **可组牌**（参与胡牌结构）= 万饼条 1-9 + 南/西/北，共 30 种；花牌一律排除在结构之外；
- 南西北是字牌：只能刻子/对子，无顺子；
- **胡牌形态两种**：
  1. 标准形：4 组面子（顺子或刻子均可）+ 1 对；
  2. 七对：7 个对子（必须门清）；
- 单吊、边张、嵌张、两面、双碰等是**听牌形式**，由向听算法自动检测，不单独建模；
- 吃只能上家（left），碰三家都可以，杠含明杠/暗杠/加杠；
- 早期设计提到"有番就能胡"——因本表底分下任何标准形胡牌都至少有底分 2/4，当前引擎将任何结构合法的胡牌判定为胡；若实际玩法另有"无番不能胡"的门槛，需用户确认后加门禁（见第 20 章待确认项）。

### 8.3 花牌机制

- 花牌**不能打出**（引擎的出牌候选永不包含花牌）；
- 抓到花牌可以选择**立刻杠**（杠分见 9.3）或**留在手里**（花牌分见 9.4）；
- **留花搏杠开**：把杠料（4 张同款花牌、暗杠料、加杠、乃至每张季节花）留到**听牌时**再杠，杠后补摸一张，补牌成胡即杠开（8 花起，上不封顶）。早杠稳拿杠分但失去杠开时机——这是本玩法最重要的择时博弈；
- 暗杠的 4 张牌面朝下不翻出，因此**暗杠后的花牌不算"花"**，只拿杠分。

## 9. 计分系统设计（花数）

### 9.1 总公式

```text
总分（花） = 底分 + Σ番型分 + Σ杠分 + 花牌分 + Σ风刻分
```

### 9.2 底分（三选一）

| 胡法 | 底分 | 说明 |
|---|---:|---|
| 自摸 | 4 | |
| 别人放炮 | 2 | |
| 杠开 | 8 | **替代**底分 2/4，不叠加（"杠开已有 8，不额外加"）；杠开是自摸胡，番型按自摸档计 |

### 9.3 番型分（叠加制；自摸档/放炮档）

| 牌型 | 自摸 | 放炮 | 判定 |
|---|---:|---:|---|
| 碰碰胡 | 10 | 5 | 4 组刻子（暗刻/碰/杠均可）+ 1 对，无吃 |
| 小吊车 | 10 | 5 | 仅 1 张暗牌 + 明牌中**有吃** |
| 大吊车 | 20 | 10 | 仅 1 张暗牌 + 4 组全是碰/杠；**独立算，不再叠碰碰胡** |
| 清一色 | 10 | 5 | 暗牌+明牌全部同一门数牌，无字牌 |
| 七对 | 10 | 5 | 7 个对子，门清 |
| 豪华七对 | 20 | 10 | 七对中一组 4 张同款当两对 |
| 双豪华 | 40 | 20 | 七对中两组 4 张同款 |

组合规则：

- 番型之间**叠加**（如清一色+碰碰胡自摸 = 4+10+10 = 24 花）；
- **大吊车独立**：全碰大吊车自摸 = 4+20 = 24 花，不另算碰碰胡；
- **七对/豪华七对/双豪华互斥**，按最高档计（豪华 = 七对里含一组 4 同款；双豪华 = 两组；"3 个一样单吊另一张"是其听牌形态，胡牌形态即 4 同款 + 5 对）。

### 9.4 杠分（每个杠单独计）

| | 万饼条 | 南/西/北 | 中发白东 |
|---|---:|---:|---:|
| 明杠 | 5 | 6 | 不可能（花牌无人打得出来） |
| 暗杠 | 10 | 12 | 12（自杠） |

### 9.5 花牌分（未杠，按同款张数阶梯）

| 中发白东同款张数 | 花 |
|---:|---:|
| 1 张 | 1 |
| 2 张 | 2 |
| 3 张 | 4 |
| 4 张 | 6 |

- **杠掉则拿杠分 12，替代手持档**（不是 12+6）——暗杠后牌面朝下不算花；
- 春夏秋冬梅兰竹菊：**每张 1 花**（无论留手里还是已设置），每张牌库仅 1 张，不存在 4 同款；
- 留 4 张（6 花）vs 杠 4 张（12 花）的差值 6 花 + 杠开可能性，构成留花博弈的核心。

### 9.6 西南北风刻

| 情况 | 花 |
|---|---:|
| 碰了 3 张南（或西/北） | +1 |
| 手里恰好 3 张南（暗刻） | +1 |
| 碰 3 张后又摸回第 4 张 → 开明杠 | +1 **升级为 +6**（替代，不是 +7） |
| 碰 3 张后把摸回的打掉 | 碰刻保持 +1 |
| **手里 4 张没碰没杠** | **0**（4 张同款组不进 4 面子+1 对，这手牌胡不了；要胡只能杠，杠有杠分） |

> 关键语义：碰后摸回第 4 张只有"开杠"或"打掉"两条路，"拿在手里不杠"的状态无法进入胡牌，不会出现在计分场景。

### 9.7 完整算例（引擎实测输出）

```text
碰碰胡+明杠南+手持3中    24花 = 自摸4 + 碰碰胡10 + 明杠南风6 + 花牌4
真清一色+碰碰胡自摸      24花 = 自摸4 + 碰碰胡10 + 清一色10
杠开碰碰胡+2花          20花 = 杠开8 + 碰碰胡10 + 花牌2
大吊车自摸              24花 = 自摸4 + 大吊车20        （不叠碰碰胡）
双豪华+杠开+1花         49花 = 杠开8 + 双豪华40 + 花牌1
留4个中 vs 暗杠4个中     11花 vs 17花（同一手牌，均含南刻1；差值即杠分12−花6）
```

## 10. 核心算法设计：向听引擎

### 10.1 约定

- **胡牌 = -1，听牌 = 0**（数学标准约定；`is_agari`/`is_tenpai` 提供语义接口）；
- 花牌在进入算法前一律剔除；
- 整体向听 = min(标准形, 七对)。

### 10.2 标准形：分解计数法

**第一步：按花色分解。** 30 种可组牌分为 4 段：万[0:9]、饼[9:18]、条[18:27]（允许顺子）、南西北[27:30]（字牌，无顺子）。

**第二步：段内递归枚举拆法。** 每种拆法产生一个 `(sets, taatsu, toitsu)` 三元组：

- 刻子（3 同）→ sets+1；
- 顺子（连续 3）→ sets+1；
- 对子 → toitsu+1；
- 搭子（相邻两张 / 隔一张的两张）→ taatsu+1；
- 孤张 → 跳过。

**第三步：Pareto 剪枝。** `(s,t,p)` 支配 `(s',t',p')` 当且仅当三分量均 ≥ 且至少一个严格大；被支配拆法可安全剔除（向听对三分量单调不增）。

**第四步：跨花色合并求和**，对每个组合套用向听公式取最小：

```text
head_bonus    = 1 if toitsu >= 1 else 0
partial_slots = taatsu + max(0, toitsu - 1)      # 留一个对子当雀头
usable        = min(partial_slots, (4 - fuuro) - sets)
shanten       = 8 - 2×fuuro - 2×sets - usable - head_bonus
```

其中 `fuuro` = 自己的明牌组数。**每一组明牌是一组已完成的面子**，因此基数下降 `2×fuuro`、面子需求降为 `4−fuuro`（实现早期曾漏掉 `-2×fuuro` 项，因 fuuro 恒为 0 未触发，明牌支持时已修复并用测试钉死）。

**公式自检**：

- 胡：sets=4, toitsu=1 → 8−8−0−1 = **−1** ✓
- 听：sets=3, toitsu=1, taatsu=1 → 8−6−1−1 = **0** ✓
- 一向听：sets=3, taatsu=1 → 8−6−1−0 = **1** ✓
- 一碰听牌：碰1组 + 暗牌 sets=2, toitsu=1, taatsu=1 → 8−2−4−1−1 = **0** ✓

### 10.3 七对（仅门清）

```text
pairs = 不同对子类型数（同款 4 张只算 1 对，余 2 张为废张）
kinds = 不同牌型数
chiitoitsu_shanten = 6 - pairs + max(0, 7 - kinds)
```

自检：7 对 → 6−7+0 = −1（胡）✓；6 对+1 单 → 6−6+0 = 0（听）✓。有明牌（fuuro>0）时七对不可能，直接跳过。

### 10.4 听牌并集（多拆法）

听牌/进张通过对每种可组牌类型"+1 后重算整体向听"得到，天然覆盖**所有合法拆法的并集**：

```text
手牌 23456（配两组完成面子）→ 听 1, 4, 7
手牌 2345666               → 听 1, 2, 4, 5, 7
  （拆法A 23456+66 听1,4,7；拆法B 2345+666 听2,5；并集）
```

这两个牌例由用户手算确认，固化为回归测试锚点。

### 10.5 公开 API

| 函数 | 说明 |
|---|---|
| `calculate_shanten(hand, fuuro=0)` | 整体向听 = min(标准形, 七对) |
| `is_agari / is_tenpai` | 胡（−1）/ 听（0）语义判定 |
| `get_ukeire(hand, fuuro)` | 进张：+1 后整体向听降 1 的牌型 |
| `get_waiting_tiles(hand, fuuro)` | 听牌时 +1 即胡的牌型（= 进张） |
| `rank_discards(hand, fuuro)` | 每张可打牌打出后的向听，升序排序 |

所有函数的 `fuuro` 默认 0，向后兼容门清场景。

## 11. 概率与风险估计

### 11.1 剩余张数（精确）

`TileCounter` 从 144 张全量出发，扣除我方暗牌、我方花牌（手持+已杠）、我方明牌、三家弃牌、三家明牌——结果对每一张牌是**精确**的可见性统计，不含任何估计。

### 11.2 风险估计（透明启发式）

`estimate_discard_risks(tile, state) -> {chi, peng, ron, label}`，返回 [0,1] 区间估计 + 三档标签（安全/中/危险）。**明确不是精确概率**，公式全部写在 docstring：

```text
chi  = 0                                    字牌（只有顺子能被吃）
     = 0.12 × suit_bias + 0.08 × shapes/3   数字牌
       suit_bias：上家（唯一能吃的人）弃牌中该门的比例——
                  弃得越多越可能不做这门，被吃概率越低
       shapes：该牌能参与几种顺子（5→3，1/9→1，中心性）

peng = 0.35 × hidden/3 × attractiveness     三家皆可碰
       hidden：该牌未可见张数（越少越难凑对）
       attractiveness：4/5/6→1.0，3/7→0.8，2/8→0.6，
                       1/9→0.5，字牌→0.7

ron  = 0                                    花牌 / 已现尽 / 现物
                                            （已被对手弃出过的牌点炮风险≈0）
     = 0.4 × shapes/3 × hidden/3            中张 × 隐藏张数，经典危险牌
```

三档标签 `discard_risk` 保留为 UI 汇总口径，与估计值一致。系数（0.12/0.35/0.4 等）是合理拍定的初始值，**可随实战感受校准**，改系数不改结构。

### 11.3 边界说明

本层不做对手手牌枚举、不做听牌推断加权（谁弃牌变少可能听牌了）——这是第 20 章路线图中的升级方向。当前模型回答的是"这张牌本身危不危险"，不是"现在谁在等这张牌"。

## 12. 杠开机会与择时杠

`find_kong_opportunities(state)` 识别四类**可择时的杠**：

| 类型 | 检测条件 | 杠分 | 决策对比 |
|---|---|---:|---|
| 暗杠料 | 暗牌中 4 张同款可组牌 | 10 或 12 | 留到听牌再杠 |
| 加杠 | 碰了 + 暗牌又摸到同款 | 5 或 6 | 风刻 +1 升级为杠分 |
| 花牌自杠（多张花） | 手持 4 张同款中发白东 | 12 | 留 4 张=6 花 vs 杠=12 花 |
| 花牌自杠（季节花） | 手持任意季节花 | 1 | 杠/留同值 1 花，价值纯在时机 |

**听牌时**追加关键提示：现在杠任意一组，补牌成胡即杠开——底分 8 花替代 2/4，且与番型/杠分/花全部叠加、上不封顶。这些量化事实注入 Prompt，LLM 据"哪些该留到听牌开、哪些该现在开"给建议。

## 13. LLM 推理层设计

### 13.1 职责边界

| 引擎负责（确定性） | LLM 负责（判断性） |
|---|---|
| 向听数/听牌/进张 | 对手牌型推断（结合弃牌与明牌） |
| 出牌候选排序 | 每个候选的攻防权衡 |
| 被吃/被碰/点炮估计值 | 风险解释与取舍 |
| 剩余张数 | 综合推荐与理由 |
| 杠开机会与量化对比 | 择时杠建议 |

**不变量**：Prompt 中所有数字由引擎注入并标注"由确定性引擎给出，请直接采信，不要重新计算"；系统提示词同样要求模型不质疑这些数字。LLM 输出**不回流**到任何引擎计算。

### 13.2 技术约束

- 官方 `anthropic` SDK，客户端零参构造（`ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` / `ant auth login` profile 解析），不硬编码 key；
- 模型默认 `claude-opus-5`，`MAHJONG_ADVISOR_MODEL` 环境变量可覆盖（交互式工具换 `claude-sonnet-5` 提速省钱是用户决定）；
- adaptive thinking（读牌推理受益于思考），`max_tokens=8192` 给思考+回答留余量；
- `stop_reason == "refusal"` 显式处理并抛可读错误；
- `client` 参数可注入——单元测试用假 client，不触网。

### 13.3 Prompt 结构

```text
系统提示：你是麻将策略助手。【计算结果】由确定性引擎给出，直接采信；
         用通俗中文，不用日式麻将术语（两面/嵌张/雀头）。

用户消息：
  【规则】        144 张构成、花牌规则、吃碰限制、两种胡牌形态
  【当前局面】    我的暗牌/明牌/花牌、上家/下家/对家弃牌与明牌、剩余总数
  【计算结果】    向听数、进张、听牌（含每张剩余）、候选出牌
                 （含被吃/被碰/点炮百分比）、杠牌/杠开机会
  请分析：
    1. 推断各对手牌型
    2. 评估每个候选的风险和收益
    3. 结合杠开机会：哪些杠留到听牌开、哪些现在开
    4. 最终推荐（3-5 个选项）及理由
```

### 13.4 降级链路

`get_advice` 抛出任何异常（无 key/断网/拒绝）→ CLI 捕获 → 打印引擎【分析结果】+ 完整 Prompt 预览。**引擎分析永远可用。**

## 22. 核心决策摘要

1. **混合架构是根本**：引擎算事实，LLM 做判断，两者职责永不混淆。
2. **本变体规则与标准麻将的根本差异**：东风与中发白是花牌（24 张花牌），胡牌结构只由万饼条+南西北（30 种）构成。
3. **向听采用自研分解计数法**：逐花色 Pareto 枚举 `(sets, taatsu, toitsu)` 合并取最小；标准形与七对取 min；多拆法听牌自动并集。
4. **明牌是向听公式的一等变量**：每组明牌使基数 −2、面子需求 −1（fuuro 项）。
5. **计分五段式**：底分（杠开 8 替代 2/4）+ 番型叠加（大吊车独立、七对系互斥）+ 杠分（明 5/6、暗 10/12）+ 花牌阶梯（1/2/4/6，暗杠替代）+ 风刻（恰好 3 张 +1，碰后第 4 张开杠升级 +6）。
6. **留花搏杠开是本玩法的灵魂机制**：所有杠分与花牌阶梯的设计都在为"早杠稳拿 vs 听牌杠搏开"的择时博弈提供量化依据，顾问层显式识别四类择时杠。
7. **正确性锚定用户手算**：引擎的每一步演进都用经用户确认的牌例固化回归测试。
